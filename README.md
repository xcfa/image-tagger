# image-tagger

Сервис ставит картинкам теги danbooru с помощью моделей Waifu Diffusion Tagger от
[SmilingWolf](https://huggingface.co/SmilingWolf) (`wd-swinv2-tagger-v3`, `wd-vit-tagger-v3`,
`wd-eva02-large-tagger-v3`, `wd-v1-4-*`). Модели работают на onnxruntime, только на процессоре. Сервис запускается в
Docker.

При первом запуске сервис скачивает модели с Hugging Face в папку `/models`. Если примонтировать её томом, при
пересоздании контейнера модели не скачиваются заново.

API — это HTTP-протокол теггера [Shizuka](https://github.com/xcfa/shizuka), но сервис ничего не знает о Shizuka и
подходит любому клиенту. Есть страница, на которой задаются пороги и проверяются картинки.

## Запуск

```bash
cp .env.example .env            # впишите TAGGER_API_KEY (не короче 16 символов) и, если нужно, HF_TOKEN
docker compose up -d            # docker-compose.yml: образ ghcr.io/xcfa/image-tagger, том ./models
docker compose logs -f          # ход скачивания; «ready», когда модели загружены
```

Или без compose:

```bash
docker run -d --name image-tagger -p 8000:8000 \
  -e TAGGER_API_KEY=… -e HF_TOKEN=… \
  -e TAGGER_MODELS="SmilingWolf/wd-swinv2-tagger-v3" \
  -v "$PWD/models:/models" ghcr.io/xcfa/image-tagger:latest
```

Страница открывается по адресу `http://localhost:8000/`.

Сервис работает от пользователя с uid 1000, поэтому у него должно быть право записи в примонтированную папку
(`sudo chown 1000 models`).

Пока модели скачиваются, `/health` и запросы тегов отвечают 503. Большая модель весит до 1,3 ГБ. Если модель не
удалось получить (такой модели нет, нужен токен, нет сети), сервис пишет причину в лог и завершается. При
`restart: unless-stopped` Docker запускает его снова.

### Подключение к Shizuka

Одна модель:

```
SHIZUKA_TAGGER_URL=http://image-tagger:8000/tag
SHIZUKA_TAGGER_KEY=<TAGGER_API_KEY>
```

Несколько моделей — каждая по своему адресу `/tag/<имя>`:

```
SHIZUKA_TAGGERS='[{"name": "swinv2", "url": "http://image-tagger:8000/tag/swinv2", "key": "…"}, {"name": "eva02", "url": "http://image-tagger:8000/tag/eva02", "key": "…"}]'
```

## Настройки

| Переменная | По умолчанию | Что задаёт |
|---|---|---|
| `TAGGER_API_KEY` (или `TAGGER_API_KEY_FILE`) | — (обязательна) | Ключ не короче 16 символов. Его требуют все вызовы, кроме `GET /health` и самой страницы: заголовок `Authorization: Bearer <ключ>`. Без ключа сервис не запускается |
| `TAGGER_MODELS` | `SmilingWolf/wd-swinv2-tagger-v3` | Модели через запятую или пробел в виде `[имя=][владелец/]репозиторий[@ревизия]`. Владелец по умолчанию — `SmilingWolf`, имя — название репозитория в нижнем регистре, ревизия — `main`. Первая модель отвечает на `POST /tag`, остальные — на `POST /tag/<имя>`. Каждая модель занимает 0,5–1,5 ГБ памяти |
| `HF_TOKEN` (или `HF_TOKEN_FILE`) | — | Токен Hugging Face (Settings → Access Tokens, хватит прав Read). Открытые модели скачиваются и без него, но анонимные загрузки быстрее упираются в лимиты. Для закрытой (gated) модели нужен токен учётной записи, которая приняла её условия |
| `TAGGER_MODELS_DIR` | `/models` | Куда скачиваются модели (`<папка>/<владелец>/<репозиторий>/`) и где лежат сохранённые пороги (`settings.json`) |
| `TAGGER_UPDATE` | `false` | `true` — при каждом запуске спрашивать Hugging Face, не изменились ли файлы модели, и скачивать изменившиеся. Если хаб недоступен, используется то, что уже скачано |
| `HF_ENDPOINT` | `https://huggingface.co` | Адрес хаба или его зеркала |
| `TAGGER_THRESHOLD` | `0.35` | Наименьшая уверенность тега, пока на странице не сохранён другой порог |
| `TAGGER_CHARACTER_THRESHOLD` | `0.85` | То же для персонажей. Порог выше, потому что модель часто путает похожих персонажей |
| `TAGGER_PORT` | `8000` | Порт HTTP |
| `TAGGER_WORKERS` | `2` | Сколько картинок обрабатывается одновременно; остальные ждут |
| `TAGGER_THREADS` | `0` | Потоки процессора на одну картинку (`0` — решает onnxruntime) |

Скачанный файл проверяется по хешу, который сообщает хаб (у больших файлов это sha256). Под своим именем файл
записывается, только когда скачан целиком. Токен уходит только на сам хаб: при перенаправлении на файловое хранилище
(другой адрес) он не передаётся.

## Страница

`GET /` — страница сервиса. На ней:

- поле для ключа (ключ хранится только в браузере);
- выбор модели;
- пороги для тегов и для персонажей. Кнопка «Сохранить» записывает их на сервер в `settings.json` в папке моделей.
  Сохранённые пороги действуют для всех запросов, в которых нет своих;
- загрузка картинки: выбор файла, перетаскивание или вставка из буфера;
- теги с оценками по группам: рейтинг, персонажи, остальные.

## API

Все вызовы, кроме `GET /health` и `GET /`, требуют заголовок `Authorization: Bearer <TAGGER_API_KEY>`, иначе ответ
401. Ошибки приходят в виде JSON `{"error": "…"}`.

### `POST /tag`

`POST /tag` (или `POST /`) обращается к первой модели, `POST /tag/<имя>` — к названной.

Запрос:
- тело — сама картинка, `Content-Type: image/jpeg | image/png | image/webp | image/gif`, до 20 МБ и 50 Мпикс;
- `X-Threshold` и `X-Character-Threshold` (0–1) — пороги этого запроса. Без них действуют сохранённые.

Ответ 200:

```json
{"model": "wd-swinv2-tagger-v3", "threshold": 0.35, "characterThreshold": 0.85,
 "tags": [{"name": "1girl", "category": "general", "score": 0.982},
          {"name": "general", "category": "rating", "score": 0.91}]}
```

Теги идут от лучшего. Категории: `general`, `character`, `rating`. Самый вероятный рейтинг (`general`, `sensitive`,
`questionable`, `explicit`) есть в ответе всегда.

Коды ошибок:
- 400 — тело пустое или оборвано;
- 411 — нет `Content-Length`;
- 413 — картинка больше 20 МБ;
- 415 — не картинка;
- 422 — картинку не удалось прочитать;
- 404 — нет такой модели;
- 503 — модели ещё скачиваются или загружаются;
- 500 — модель сломалась на этой картинке.

### Остальные вызовы

- `GET /models` — список моделей: `name`, `repo`, `revision`, `default`, `ready`. У готовых моделей ещё `size`
  (сторона входа модели) и `tags` (сколько тегов знает модель).
- `GET /settings` и `PUT /settings` `{"threshold": 0.35, "characterThreshold": 0.85}` — сохранённые пороги. В `PUT`
  можно передать одно поле.
- `GET /health` — 200 `{"status": "ready"}`, когда все модели готовы, до этого 503. Его использует `HEALTHCHECK`
  образа.

## Разработка

```bash
python -m venv .venv && . .venv/bin/activate
pip install -r requirements-dev.txt
ruff check . && ruff format --check . && python -m pytest -q
```

Тесты не ходят в сеть:
- модель в тестах — крошечная настоящая ONNX-модель той же формы, что WD; её собирает пакет `onnx`;
- Hugging Face заменяет поддельный сервер из `tests/conftest.py`. Он отвечает как хаб: на большие файлы — 302 с
  `X-Linked-Etag` на хранилище, на маленькие — 200 с git-хешем;
- `tests/test_main.py` запускает `python -m tagger` целиком.

CI (`.github/workflows/ci.yml`) запускает ruff и тесты, а в PR ещё собирает образ. Публикация (`publish.yml`)
выкладывает образ для amd64 и arm64 в `ghcr.io/xcfa/image-tagger`: с master — тег `latest`, с git-тега `v1.2.3` —
`1.2.3`, `1.2` и `1`.
